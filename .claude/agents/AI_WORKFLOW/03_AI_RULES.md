# 📏 AI 行为准则与底线

所有 Agent 在工作时必须遵守以下规则：

1. **文档驱动**：任何代码的修改，必须先有对应的 PRD 或设计文档更新，严禁凭空写代码。
2. **拒绝硬编码**：严禁在代码中硬编码密钥、Token 或绝对路径；使用配置文件或环境变量。
3. **保持简洁**：遵循 KISS (Keep It Simple, Stupid) 原则，不要过度设计。
4. **中文沟通**：所有的文档、注释、以及 Agent 之间的对话，默认使用简体中文。
5. **诚实反馈**：如果当前需求存在技术风险或逻辑矛盾，评审员必须第一时间指出，而不是强行推进。
6. **代码审查**：功能开发完成后必须进行代码审查，修复问题后才能提交。

## 代码审查检查清单

每次代码评审必须检查以下项目：

| 类别 | 检查项 |
|------|--------|
| 安全 | 全局变量/外部输入是否进行空值检查？ |
| 安全 | 数组键访问是否使用 `get()` 或 `unwrap_or()`？ |
| 安全 | 错误处理是否使用 `Result`/`Option` 而非 unwrap？ |
| 健壮 | 是否有不必要的重复计算？ |
| 性能 | 是否有不必要的堆分配？ |
| 可维护 | 重复代码是否已抽取为公共组件？ |
| 可维护 | 模块职责是否单一？ |
| 可维护 | 错误类型是否实现了 `std::error::Error`？ |

## Rust 实现约束

#### 1. 错误处理

- **必须使用 `Result`/`Option`**：不得使用 `.unwrap()` 除非确定不会失败
- **自定义错误实现 `std::error::Error`**：便于错误链传递
- **错误日志记录**：使用 `log::error!` 等记录错误信息

示例：
```rust
// ❌ 禁止 - unwrap 可能 panic
let value = some_result.unwrap();

// ✅ 正确 - 使用 ? 运算符传播错误
let value = some_result?;
```

#### 2. 模块划分

- **一个模块只做一件事**：模块职责清晰，避免上帝模块
- **crate 内部模块命名**：使用 `mod_name` 而非 `mod-name`
- **公开 API 使用完整路径**：如 `crate::gateway::IEC104`

#### 3. 生命周期

- **避免不必要的 `'static` 约束**：除非确实需要
- **引用生命周期明确**：结构体中引用需标注生命周期

#### 4. 并发安全

- **必须 `Send`/`Sync`**：跨线程数据类型需实现相应 trait
- **使用锁代替 `Mutex` 内部可变**：明确锁的边界
- **避免数据竞争**：使用 Arc 而非 Rc

#### 5. 依赖管理

- **依赖必须声明在 `Cargo.toml`**：严禁直接修改 Cargo.lock
- **避免过度依赖**：优先使用标准库，第三方依赖需评审

#### 6. 测试规范

- **单元测试放在同文件**：`#[cfg(test)]` 模块
- **集成测试放在 `tests/` 目录**
- **测试函数以 `test_` 开头**：或使用 `#[test]` 属性

#### 7. 文档注释

- **公共函数/类必须有文档注释**：使用 `///` 或 `/** */`
- **复杂算法注释关键步骤**：说明边界条件和假设
- **TODO/FIXME 标注待处理事项**：便于追踪

#### 8. 安全约束

- **不得硬编码密钥**：使用环境变量或配置加密
- **国密算法优先**：SM2/SM4 加密，SM3 哈希
- **双向证书认证**：TLS 连接需验证证书

## 常见反模式

| 反模式 | 正确做法 |
|--------|----------|
| `.unwrap()` 滥用 | 使用 `?` 运算符或 `unwrap_or()` |
| `Rc<RefCell<T>>` 跨线程 | 使用 `Arc<Mutex<T>>` |
| 硬编码路径 | 使用 `std::env::var()` 环境变量 |
|上帝模块| 按职责拆分为多个模块|
| 不实现 `Error` trait | 自定义错误实现 `std::error::Error` |
