# AI 协作工作流规范 (V2 - 合同与路径驱动)

> ⚠️ **核心原则**：**交付物驱动，质量门禁控制**。每个阶段的进入条件是获得上一阶段的“合同交付物”，出口标志是产出本阶段的“合同交付物”并获得通过标记。严禁跳过门禁。

**路径选择指南**：

* **路径A (标准功能项目)**：当项目涉及**前后端交互、新增API/UI、数据库变更**时使用。
* **路径B (简单修改项目)**：当项目仅涉及**1-2个文件修改、修复Bug、无结构变更**时使用。**(快速通道)**
* **路径C (纯后端/前端项目)**：当项目明确**只涉及后端API或前端UI其中一端**时使用。在路径A基础上，省略另一端的设计评审等待。

## 路径A：标准功能项目工作流

### 阶段一：需求与设计 (必须串行)

1. **需求启动**

   * **输入**：用户原始需求。
   * **合同**：产出标记为 `[REVIEWED: PASS]` 的PRD文档。
   * **角色**：需求分析师 -> 需求评审员。
   * **输出**：`docs/superpowers/specs/YYYY-MM-DD-需求名-PRD.md`
2. **系统设计 (并行-可选)**

   * **输入**：`[REVIEWED: PASS]` 的PRD。
   * **合同**：产出标记为 `[DESIGN_APPROVED]` 的**技术设计文档**。*（若需UI，则还需产出标记为 `[DESIGN_APPROVED]` 的UI设计文档）*
   * **角色**：
     * *后端线*：架构师 -> 设计评审员。
     * *前端线 (如果需要)*：UI/UX设计师 -> UI评审员。
   * **同步点**：必须获得**所有必需**的设计批准标记，才能进入开发。如果项目无需UI，则只需技术设计批准。

### 阶段二：开发、质量门禁与交付

3. **并行开发**

   * **输入**：`[DESIGN_APPROVED]` 的所有设计文档。
   * **角色**：开发工程师（前端/后端）。
   * **说明**：双方基于协商好的接口规范进行开发。
4. **代码评审 (强制门禁)**

   * **输入**：开发工程师提交的代码变更。
   * **合同**：获得标记为 `[CODE_REVIEWED: PASS]` 的代码评审报告。
   * **角色**：项目经理调度 -> 代码评审员。
   * **工具**：必须使用 `request-code-review` 技能进行正式评审。
5. **自动化测试**

   * **输入**：`[CODE_REVIEWED: PASS]` 的代码。
   * **合同**：获得标记为 `[TEST_PASSED]` 的测试报告。
   * **角色**：自动化测试工程师。
   * **失败处理**：测试失败则打回开发工程师修复，并重新进行代码评审。
6. **重构验证与交付**

   * 执行重构检查清单。
   * 验证通过后，由项目经理通知用户交付。

## 路径B：简单修改项目工作流 (快速通道)

1. **问题分析与简易设计 (可选)**
   * **输入**：Bug描述或简单需求。
   * **角色**：开发工程师可进行简单技术评估，如需方案决策可咨询架构师。**不强制产出设计文档**。
2. **开发**
   * **输入**：明确的问题描述或简易设计方案。
   * **角色**：开发工程师。
3. **代码评审 (强制门禁)**
   * **同路径A**。**此步骤不可省略**。
4. **自动化测试**
   * **同路径A**。应运行受影响功能的回归测试。
5. **交付**

## 路径C：纯端项目工作流

在**路径A**的基础上进行简化：

* 在**阶段一**，只需完成所需一端（后端或前端）的设计与评审。
* 在**阶段二**，仅需该端的开发工程师进行开发。
* **质量门禁**（代码评审、测试）**依然强制执行**。

## 通用规则与红线

1. **标记即合同**：只有带有正确通过标记的文档，才是有效的阶段出口凭证。
2. **评审不通过**：任何评审环节（需求、设计、代码）若未通过，必须打回上一责任角色修改，**严禁带病进入下一阶段**。
3. **技能是工具**：各角色为完成“合同”，可自主选用 `brainstorm`, `write-plan` 等技能，这不是流程的检查点。
4. **经理是路由**：项目经理负责在项目启动时选择路径，并在每个阶段结束时检查“合同”标记，决定是否推进。
