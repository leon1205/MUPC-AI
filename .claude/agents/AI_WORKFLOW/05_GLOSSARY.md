# AI 协作框架术语与技能词典

> 本文件定义了团队协作中的核心概念、交付物状态和可用技能，是理解整个工作流的基础。

## 1. 核心交付物与状态标记


| 标记                    | 全称         | 含义                                                  | 应用场景                 |
| :---------------------- | :----------- | :---------------------------------------------------- | :----------------------- |
| `[REVIEWED: PASS]`      | 需求评审通过 | 需求文档(PRD)已通过评审，清晰、完整、可进入设计阶段。 | PRD 文档顶部             |
| `[DESIGN_APPROVED]`     | 设计已批准   | 技术设计或UI设计已通过评审，可作为开发依据。          | 技术设计或UI设计文档顶部 |
| `[CODE_REVIEWED: PASS]` | 代码评审通过 | 代码变更已通过评审，符合质量与安全规范，可进入测试。  | 代码评审报告或提交记录   |
| `[TEST_PASSED]`         | 测试通过     | 相关功能已通过自动化测试，达到交付标准。              | 测试报告                 |

## 2. 可用技能 (Superpowers)

技能是AI代理可调用的工具，用于完成特定类型的思考或创作任务。


| 技能名称                  | 主要用途                                                             | 典型输入                                                               | 期望输出                                                     | 主要调用角色               |
| :------------------------ | :------------------------------------------------------------------- | :--------------------------------------------------------------------- | :----------------------------------------------------------- | :------------------------- |
| **`brainstorm`**          | **探索与发散**。针对开放式问题或模糊需求，生成多种可能性并分析权衡。 | “如何实现X功能？” “有哪几种技术方案？”                             | 多个选项列表，包含各自的优缺点（性能、成本、扩展性等）分析。 | 需求分析师、架构师         |
| **`write-plan`**          | **规划与收敛**。基于明确的目标，生成结构化、可执行的步骤计划。       | “这是PRD，请制定开发计划。” “这是选定的技术方案，请输出详细设计。” | 一份包含任务分解、资源预估、实施步骤的详细计划文档。         | 需求分析师、架构师         |
| **`request-code-review`** | **质量门禁**。对代码变更进行系统性审查，发现安全、规范和设计问题。   | 代码变更diff、相关设计文档。                                           | 代码评审报告，包含问题分类（严重/警告/优化）和具体修改建议。 | 项目经理（调度代码评审员） |

## 3. 项目类型定义


| 项目类型            | 特征                                               | 适用工作流路径                |
| :------------------ | :------------------------------------------------- | :---------------------------- |
| **标准功能项目**    | 涉及前后端交互、有新增API或UI、需修改数据库。      | **路径A**                     |
| **简单修改项目**    | 仅修改1-2个文件、修复Bug、无结构变更、无新增接口。 | **路径B**                     |
| **纯后端/前端项目** | 仅涉及单一端的技术变更，无需另一端配套设计。       | **路径C** (在路径A基础上简化) |
