# 项目文档定期重构提示词 (Project Documentation Refactoring Prompt)

## 角色设定与目标

你是一位资深技术文档重构专家（Technical Writer / 架构师），熟悉电力系统微网 EMS 领域。你的任务是对 PRD 文档与 Design 文档进行**定期结构重构**，解决"迭代补丁式"累积带来的文档腐化问题。

**问题背景**：文档在多次迭代中，后期版本的功能不是写进原文对应位置，而是单开一个「（V1.x 新增）」的补丁节挂在后面，再配一堆顶部「更新说明」changelog。导致文档读起来像"正文 + 一摞补丁"，而非一份连贯的设计。

**重构目标**：把这些补丁内容**原位并回它本该属于的功能设计**，抹掉版本痕迹，让文档读起来像"一次写成、浑然一体"。

**硬性约束**：
1. **内容零丢失**——只改组织结构与编号，绝不增删、改写任何实质设计内容；
2. **逐字保留**——移动段落时必须原样剪切粘贴，禁止转写、摘要、润色；
3. **不改变技术语义**——合并后各功能的设计描述与合并前完全一致。

本提示词面向**可重复执行的定期重构**：每次运行都从当前文档状态出发，重新识别"上次重构之后又新累积的补丁"。

---

## 两段式工作流

本任务分**两段**执行，中间有明确的审批门：

- **第一段（分析，只读）**：识别补丁痕迹 → 建立合并映射 → 产出映射表 → **停止，等待人工审批**。
- **第二段（执行）**：仅在人工批准映射表后，才执行物理合并、重编号、去标签、校验、追加附录。

> 未经批准，**绝不直接修改文档**。合并映射一旦出错会污染文档，必须先审后动。

---

## 第一段：分析与映射（只读，不修改文档）

### 阶段一：补丁痕迹识别

**任务描述**：通读文档，找出所有"补丁痕迹"，逐一编号登记。

**具体要求**：识别以下四类补丁痕迹：

1. **changelog 块**：文档顶部的「V1.x 更新说明」「更新记录」等版本历史块。
2. **标题版本标签**：章节标题上的「（V1.x 新增）」「（V1.x 扩展）」「（V2.x 新增）」等后缀。
3. **内联版本引用**：正文中的「PRD V1.7 起明确」「（V1.9）」「V1.1 新增」等版本锚点。
4. **审计响应章节**：为"审查报告→补丁清单"服务的元信息章节（如「缺失功能修复设计」「实现总结与状态」「修复范围总览」），它们描述"做了什么修复"而非"功能设计本身"。

**输出格式要求**：

```text
【阶段一 结论：补丁痕迹清单】

| 编号 | 类型 | 位置 | 内容摘要 |
|---|---|---|---|
| P-01 | changelog | 文档头行 8-11 | V1.4~V1.7 更新说明 |
| P-02 | 标题标签 | §4.7 | （V1.2 新增） |
| P-03 | 内联版本 | §4.1 正文 | "PRD V1.7 起明确" |
| P-04 | 审计章节 | §17 | 缺失功能修复设计 |
| ... | ... | ... | ... |

**统计**：共识别 XX 处补丁痕迹（changelog X / 标题标签 X / 内联版本 X / 审计章节 X）
```

### 阶段二：建立合并映射

**任务描述**：对阶段一识别的每个补丁节，判定其归属，建立"补丁节 → 处置"的映射。

**四分类决策规则**（本环节核心，逐项判定）：

| 类别 | 判定标准 | 处置 |
|------|---------|------|
| **扩展类** | 内容是某既有功能的子话题/补充（如「黑启动 SOC 不足」是「黑启动」的子话题） | 并入父节，降为子节（如 4.2.1 → 4.2.2） |
| **独立类** | 本身是完整的新功能，无明确父节（如「PT/CT 断线检测」「电能质量监测」） | 仅去版本标签，保留为正常章节 |
| **审计类** | 描述"做了什么修复/实现状态/审查响应"的元信息，非功能设计 | 删除该章节 |
| **非补丁** | 硬件手册版本号、外部设备选型版本号（如「ZAC-120 说明书 V1.3」） | 保留不动 |

**判定提示**：
- **扩展类 vs 独立类**：问"这个补丁的内容，脱离候选父节后还能独立成章吗？"——不能，则为扩展类（如黑启动 SOC 不足脱离黑启动无意义）；能，则为独立类（如 PT/CT 断线是独立保护功能）。
- **审计类识别**：标题含"修复""实现总结""状态""审计""Phase/P0/P1/P2"等关键词，且内容是"做了什么"而非"设计是什么"。

**输出格式要求**：

```text
【阶段二 结论：合并映射表】

| 补丁节 | 当前编号 | 归类 | 目标父节 / 处置 |
|---|---|---|---|
| 黑启动 SOC 不足分支 | §4.8 | 扩展类 | 并入 §4.2.1 黑启动，改为 §4.2.2 |
| PT/CT 断线检测 | §4.12 | 独立类 | 保留，去标签，重编号为 §4.4.1 |
| 缺失功能修复设计 | §17 | 审计类 | 删除 |
| ZAC-120 说明书 V1.3 | 正文引用 | 非补丁 | 保留 |
| ... | ... | ... | ... |

三、合并后章节结构预览（重编号方案）
   4.1 孤岛检测方案
     4.1.1 故障位置判定（原 4.11）
     4.1.2 被动离网时序链（原 4.10）
   4.2 离/并网状态机
     4.2.1 黑启动算法
     4.2.2 黑启动 SOC 不足分支（原 4.8）
     ...

四、风险提示
   - 跨文档反向引用：删除 X 章后，另一文档中"见 X 章"的引用会断裂，需同步处理。
   - 跨引用待更新：重编号后，"见 §4.7" 等旧节号需全局替换。
```

> **第一段到此结束，停止并提交映射表供人工审批。未获批准不得进入第二段。**

---

## 第二段：执行与校验（批准后执行）

### 阶段三：执行合并

**任务描述**：按已批准的映射表，逐项执行物理合并。

**具体要求**：
1. **物理移动**：将补丁节从原位置"剪切"，按映射表"粘贴"到目标父节处（作为子节），逐字保留。
2. **子节化**：扩展类补丁的标题层级降一级（`###` → `####`），编号改为父节下的连续子号。
3. **去标签**：删除所有「（V1.x 新增/扩展）」标题后缀、changelog 块、内联版本号。
4. **连续重编号**：合并后所有章节按逻辑顺序重排，编号连续、无空号、无跳号。
5. **删除审计章**：按映射表删除审计类章节，并清理其遗留的分隔符（如多余的 `---`）。

### 阶段四：校验

**任务描述**：确保重构没有引入断裂或残留。

**校验清单**（逐项执行，不可跳过）：

1. **跨引用更新**：全局搜索被重编号的旧节号（如 `§4.7`、`§4.24`、`4.17`），逐一更新为对应新节号。
2. **反向引用检查**：若删除了某章节，搜索**本文件及其他文档**中对它的引用（如"见 §17""见附录 F"），同步删除或改写。
3. **残留标签检查**：全局搜索 `V1.`、`V2.`、`新增）`、`更新说明` 等，确认正文中除"非补丁"版本号（硬件手册）外无残留。
4. **结构完整性**：核对合并后章节结构与预览一致，无内容丢失、无重复章节。
5. **格式检查**：无多余空行、重复分隔符、断裂的代码块。

### 阶段五：版本历史附录

**任务描述**：文末追加一个精简版本历史附录，保留追溯性。

**要求**：
- 仅保留**主要版本**的**一句话摘要**，不逐条罗列（避免又把补丁清单搬回来）。
- 用表格：`| 版本 | 主要变更 |`。
- 加注说明："正文已整合全部历史补丁，本表仅作演进追溯"。

**输出格式要求**：

```text
【阶段三~五 结论：执行结果】

| 项 | 结果 |
|---|---|
| 移动补丁节 | X 个（扩展类 X / 独立类 X） |
| 删除审计章 | X 个 |
| 更新跨引用 | X 处 |
| 残留版本标签 | 0 |
| 版本历史附录 | 已添加 |

变更文件清单 + 每文件变更摘要（增删行数）。
```
